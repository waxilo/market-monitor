# 行情来源的「独立性」盘点 · 可新接入的永续接口

日期：2026-09-29
范围：桌面端 `desktop/src/lib/{sources,dialects}.ts` 与 Android `FuturesEndpoint.kt` —— 两端共用**同一份**候选清单

需求原文：

> 现在行情的来源有蛮多的，但是币安的接口太多了，他们都是一起有效一起失效，再找找有没有其他的可以接入

---

## 一、问题定性：候选清单的长度 ≠ 容灾能力

现有 12 个候选，按**后端归属**折叠后只剩 **7 个真实来源**：

| 分组 | 候选 | 真实来源数 |
| --- | --- | --- |
| 币安同构 | Aster 官方、币安主域、镜像 1/2/3、老镜像 | **1**（`/fapi/v1` 同一套后端与可达性） |
| 独立盘口 | OKX、Bybit、Bitget、Gate、MEXC、Hyperliquid | **6**（协议各异，互不同生共死） |

也就是说：**一半的候选席位押在同一个后端上**。币安全族一旦不可达，用户看到的可用源会从「12」瞬间掉到「6」，
而探测弹窗里那 6 行红色并不提供任何额外信息 —— 它们是同一条链路的 6 个观测点。

### 用本机网络实测印证（不走代理）

| 域名 | 结果 |
| --- | --- |
| `fapi.binance.com` / `fapi1~3` | 连接超时 |
| `fapi.binancefuture.com` | 域名解析失败 |
| `fapi.asterdex.com` | 连接重置 |
| `api.gateio.ws` | **200** |
| `api.hbdm.com`（火币）等新候选 | **200**（见下表） |

币安系 **6/6 全红**、非币安系照常 —— 用户观察到的「一起有效一起失效」得到确认。

> ⚠️ 本次 Aster 也不可达，与早先「Aster 大陆通常可直连」的结论不一致。这属于**本机当前网络环境的特例**，
> 不能推广成普遍结论，也别据此从清单里删 Aster。

## 二、探测方法与口径

- 本机 `http_proxy` 指向 WorkBuddy 代理，而 **node 的 `fetch` 默认不读代理变量** ⇒ 脚本天然测的是**直连**；
  走代理那一份另用 `curl --proxy` 对照（结论：代理下 Gate / HTX / Bitunix / Phemex / CoinEx 通，
  币安 / OKX / Bybit / Bitget 仍不通 —— 该代理不代表用户的 VPN，只作参考）。
- 判定「可接入」的门槛是四件套齐全：**K 线 + 单标的 24h + 全量 24h 快照 + 交易对与价格精度**。
- **周期白名单必须配非法值对照**：对不认识的枚举，第三方接口常返 200 并悄悄回落，所以「返 200」不是「支持」，
  必须同时确认明显非法值被拒。Bitunix 的形态尤其危险 —— 非法 interval 返 `code:0` + `data:[]`。

## 三、实测结果

### 可接入（直连可用 + 四件套齐全）

| 来源 | K 线 | 单标的 24h | 全量 24h | 精度 | 周期白名单 |
| --- | --- | --- | --- | --- | --- |
| **HTX 火币** | `/linear-swap-ex/market/history/kline` | `/market/detail/merged` | `/market/detail/batch_merged` | `swap_contract_info.price_tick` | 14 个：`1min 3 5 15 30 60min 2 4 6 12hour 1day 3day 1week 1mon`（`1year` 被拒） |
| **Bitunix** | `/api/v1/futures/market/kline` | 无（用全量筛） | `/api/v1/futures/market/tickers` | `trading_pairs` 的 `basePrecision/quotePrecision` | 15 个：`1m 3 5 15 30m 1 2 4 6 8 12h 1d 3d 1w 1M`（全支持） |
| Phemex | `exchange/public/md/v2/kline/last` | `/md/v2/ticker/24hr?symbol=` | `/md/v2/ticker/24hr/all` | 需从 2.5MB 的产品表筛 | 秒数制，全支持；非法值 400 |

**关键细节（接入时必须照做）**

- **HTX**：K 线行 = `id`(秒) / `open` / `close` / `high` / `low` / `amount`(基础币) / `vol`(张) / `trade_turnover`(计价币)，
  **升序返回**；全量快照自带 `open` 字段 —— 无需像 Gate / Bybit / MEXC 那样靠 `last − change` 还原 24h 开盘，
  是现有方言里最干净的一家。非法 `period` 返 `200 + status:"error"`（**业务码在 `status` 里，不在 HTTP 状态里**）。
- **Bitunix**：K 线行 = `open/high/low/close/quoteVol/baseVol/time`(ms)，**降序返回**（需倒序）；
  全量 ticker 自带 `open`。**非法 `interval` 返 `code:0` + `data:[]`** ⇒ `parseKlines` 判定必须看数组非空，
  只看业务码会把「不支持」读成「支持干净的空结果」。
- **Phemex**：K 线行的价格字段序（open/close/high/low）尚未逐字段核对；产品接口 2.5MB，启动成本高。

### 探测过但排除

| 来源 | 排除原因 |
| --- | --- |
| CoinEx | `BTCUSDT` 状态 `online` 却 `is_market_available:false`，K 线返空数组 —— **能连通、没行情** |
| Deribit | 仅 BTC / ETH 永续，且**反向合约**，非 USDT 本位，与「只做 USDT 本位」口径不符 |
| Paradex | **USDC 本位** + 市场列表 7MB（含大量期权） |
| GMX v2 | 链上预言机报价，**没有 K 线**，无法支撑图表 |
| BingX / BloFin | CDN 直回 403 |
| WOO X / Backpack / dYdX / Lighter / KuCoin / BitMart / XT | 直连不可达（超时 / 连接重置） |
| CoinGecko / CoinCap / CryptoCompare | 聚合源同样不可达，且非交易所直连盘口 |

## 四、建议

按用户一贯的「重构式改动」偏好，建议一次性把候选清单的**结构**理顺，而不是零散加两行：

1. **新接入 HTX 与 Bitunix**（`HUOBI` / `BITUNIX` 两个方言）—— 直接复用现有方言模式：
   每方言实现 `ladder / probe / klines / ticker / allTickers / exchangeInfo` 与对应 parse，两端各加一份
   （TS 在 `desktop/src/lib/dialects.ts`，Kotlin 在 `data/remote/dialect/FuturesDialects.kt`）。
2. **币安系从 6 个精简到 2 个**（保留 `fapi.binance.com` 主域与 Aster，删掉镜像 1/2/3 与老镜像）——
   它们提供的是同一条链路的重复观测点，删掉不损失容灾能力，却能让探测弹窗一眼看清「哪几家真的独立」。
3. 精简后候选总数基本持平，真实独立来源从 **7 → 9**（含 Phemex 则 10）。

**验证要点**：两端各自补单测（周期映射、非法值形态、字段序）；真机复核探测弹窗能正确区分
「币安全族不可达」与「只是这一家不可达」。

清单最终形态（两端一致，10 个）：

```
Aster 官方 / 币安合约 主域          ← 币安同构，2 个席位
OKX / Bybit / Bitget / Gate / MEXC / Hyperliquid / HTX 火币 / Bitunix
```

被删掉的 4 个镜像**不需要迁移逻辑**：两端 `normalize()` 本来就把「不在清单里的旧值」回落到默认源，
用户原先若选了镜像，升级后自动回到出厂默认。

### 实现时踩到的三件事（都已按实测处理）

1. **`from`/`to` 在 HTX 上无效**。用「明显过期的窗口」（`from=1790000000`）请求，回来的仍是当下最新 5 根；
   `start`/`end` 同样。⇒ HTX 的 `klines` **不传时间窗**，并新增 `supportsTimeWindow = false`。
   这不是洁癖：`olderKlines` 的 `hasMore` 是按「返回条数是否满额」算的，HTX 每次都满额 ⇒
   若不拦住，用户把图拖到最左会**无限重复请求**同一批数据。
2. **两家「不支持」的形态完全不同**，解析层必须分别兜住：
   - HTX：`HTTP 200 + status:"error"`（业务码在 `status`，不在 HTTP 状态里）⇒ 必须抛；
   - Bitunix：`code:0 + data:[]`（不报错也不回落）⇒ **没抛异常不等于周期被支持**，靠白名单挡。
3. **Kotlin 的块注释支持嵌套**：在 KDoc 里写 `` `...market/*` `` 会把这个 `/*` 当成嵌套注释的开始，
   整块注释闭合不上，报 `Unclosed comment` 且行号指向文件末尾（很难联想到这里）。文案里不要出现 `/*`。

### 验证

- **桌面端**：`tsc --noEmit` 通过；另写两个脚本用**真实响应**驱动 `parseKlines` / `parseTicker` /
  `parseAllTickers` / `parseExchangeInfo`（Node 22 原生 strip-types 直接 import `.ts`）——
  Bitunix + Gate 回归 **25 项断言全绿**、HTX **30 项全绿**。断言的是「值正确」（价格量级、字段列位、
  升序、tickSize），不是「没抛异常」。
- **Android**：`./gradlew :app:testDebugUnitTest` → **265 个用例全绿**（含本次新增 13 个）。
  样本全部是真实响应原文（含 Bitunix 原生降序、HTX 的 `invalid size` 错误体）。
  过程中真被测试抓到一处自己的错：符号断言漏写了 `PEPEUSDT`（实际 3 个币）——
  这类「期望值写错」正是它该抓的。
- **HTX 的样本来源**：本机直连被 DNS 污染，样本经中转取回后**原样**写进单测与验证脚本，
  注释里已标注来源。

> ⚠️ **本机跑 Android 构建要绕开 IDE**：用户开着 IDEA（`com.intellij.idea.Main`），它会占住
> `android/app/build/tmp/kotlin-classes`，Gradle 报「另一个程序正在使用此文件」而失败 ——
> `./gradlew --stop` 只能停 Gradle daemon、停不掉 Kotlin daemon。**不要为此杀 java 进程**（IDEA 与它的
> `RemoteMavenServer` 都在同一个 `jps` 列表里）。可行的做法是把构建输出整体挪走：
>
> ```bash
> JAVA_HOME="C:/Users/sloan.wang/.jdks/ms-17.0.19" ./gradlew :app:testDebugUnitTest \
>   -I ../.workbuddy/tmp/init-builddir.gradle --project-cache-dir ../.workbuddy/tmp/agcache
> ```
>
> 其中 `init-builddir.gradle` 把 `allprojects.buildDir` 指到 `.workbuddy/tmp/agbuild`，原 `app/build` 一动不动。
>
> 更省事的**等价做法**（同日复盘实测有效）：把 `app/build` 下那三个被占的目录
> （`tmp/kotlin-classes`、`kotlin`、`kspCaches`）**改名走**（`os.rename` 到 `.stale-<时分秒>`，改完回读确认），
> Gradle 就会在新路径上重建，而 IDEA 抓的仍是旧路径 —— 不必改 `buildDir` 也能接着跑。
> 另外提醒：**同一项目一次只跑一个 Gradle**（并发的两个会互相抢同一批目录），
> 且 `./gradlew --stop` 会把正在跑的那个也停掉（它的失败文案是
> `Gradle build daemon has been stopped: stop command received`，别当成第二个问题）。
