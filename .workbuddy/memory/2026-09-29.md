## 桌面端（续）：遮罩卡住 + 任务栏遮挡

用户两条反馈：①「遮罩有时候鼠标不在上面也显示，像卡住」②「悬浮窗放在任务栏上，再点任务栏，悬浮窗会被覆盖」。

### 1. 遮罩改成显式状态（不再用 CSS `:hover`）
新增 `hooks/useOverlayReveal.ts`：`pointermove` 才能点亮；离开面板 / 窗口失焦 / 页面不可见 / 视口 resize / Tauri 的 `onMoved`·`onResized`·`onFocusChanged(false)` 一律熄灭；默认熄灭。`MiniApp` 给 `.mini` 加 `revealed` 类，theme.css 的 `.mini:hover .mini-overlay` → `.mini.revealed .mini-overlay`，行的 hover 底色同样收进 `.revealed`。
- 根因：`:hover` 只在浏览器真收到鼠标消息时更新，而这个窗口会自己移动（拖拽 / 按条数改高度时下边缘不动⇒上边缘在跑）和隐藏，鼠标位置在那之后离开窗口时 **Chromium 再也不发 `mouseleave`** ⇒ `:hover` 永久卡亮。
- 指针事件挂在**面板元素**上而不是 window：要的是「指针在面板上」，视口比面板大时两者结论不同。

### 2. 压住任务栏（`lib.rs` 的 `taskbar` 模块 + `watch_mini_above_taskbar`）
- `is_buried_by_taskbar(hwnd)`：沿 `GetWindow(GW_HWNDPREV)` 只遍历 topmost 组（碰到第一个非 topmost 就停，topmost 永远在非 topmost 之上），遇到 `Shell_TrayWnd`/`Shell_SecondaryTrayWnd` 即被压住。
- 500ms 心跳线程 + `run_on_main_thread`：**只在真被压住时**用 `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE|NOSIZE|NOACTIVATE)` 提回去；无条件重设会周期性压住开始菜单等其它 topmost 窗口。
- 为什么必须轮询：任务栏被点击/激活时被 shell 提到最前，**这件事不会给应用发任何事件**（用户点的是任务栏，连 `Focused(false)` 都收不到）。
- Cargo.toml 加 `[target.'cfg(windows)'.dependencies] windows = "0.62"`（与 tauri 同版本，复用 lock 里的 0.62.2，不新增下载）。

### 验收
- `npm run build` ✓、`cargo test` 8/8 ✓（新增两条任务栏类名断言）。
- `verify-desktop-ui.mjs` **21/21**（新增 4 条遮罩开关断言：默认不显示 / 指针离开熄灭 / 失焦熄灭 / 尺寸变了熄灭 / 还能再点亮）。
- 新写 `verify-mini-taskbar.py`（真机 z 序判定）**全过**：复现「任务栏压住悬浮窗」→ 心跳 0.2~0.4s 纠正；任务栏处于激活态时同样有效。

### 排查过程中的三个关键发现
1. **`set_always_on_top(true)` 重复调用无效**：tao 的 `set_window_flags` 有 flags 去重（`diff == empty` 直接 return），`ALWAYS_ON_TOP` 早置位 ⇒ 根本走不到 `SetWindowPos`，必须自己调 Win32。
2. **对已经是 topmost 的窗口直接提 `HWND_TOPMOST` 也可能是 no-op** ⇒ 复现脚本先降 NOTOPMOST 再升 TOPMOST 才稳（且成功率约一半，必须**重试到真的被压住**，否则「没被压住」会被算成「已纠正」= 假绿，我第一次跑就吃了这个）。
3. 用**类名伪装成任务栏**的假窗口（ctypes `RegisterClassExW` + `CreateWindowExW("Shell_TrayWnd")`）把「判定 + 纠正」从「真实任务栏能不能被越过」里分离出来，才确定链路本身正常 —— 打包的 python 没有 tkinter。

## 傍晚：发版模型改成「每端一个固定通道 Release」+ 发桌面端 0.1.2

用户要求：把 Releases 清空，只留「一个 app + 一个桌面端」两个；以后每次发新版**只换里面的产物、不新建 Release**。
旧状态是两套写法各堆一串 —— 桌面端每次 `gh release delete` + `create`（每次都产生新 Release），
Android 每版按 tag 建一个，**已经堆到 39 个**（0.2.0 … 0.9.26 + desktop-v0.1.0 + desktop-latest）。

### 一、固定通道怎么落
- 新增 `.github/scripts/publish-channel.sh`（两端共用）：**通道不存在才创建**，存在就先**清掉上一次的全部产物**再传新的。
  ⚠️ 必须清：产物名带版本号（`market-monitor_0.1.1_windows.exe` → 下一版名字就变了），
  `gh release upload --clobber` 只覆盖同名文件，不清就会新旧并存、用户可能下到过期包。
- Android：`release.yml` 发到固定 tag `android-latest`。**版本号改由产物名承载**（`market-monitor-<version>.apk`），
  因为通道 tag 恒定、不再带版本。App 侧 `VersionCompare.versionFromAssetName` 从文件名读
  （取第一个 `数字.数字[.数字]`；`arm64-v8a` 这类 ABI 名不含点，所以 ABI 后缀加在版本后面是安全的）。
  另加断言：tag 版本必须 == `build.gradle.kts` 的 `versionName`，不一致直接红。
- Android App：`GithubReleaseApi.latestRelease()` → `channelRelease()`，`/releases/latest` → `/releases/tags/android-latest`；
  `ReleaseInfo.version`（读 tag）→ `apkVersion()`（读产物名）。

## 插曲：推文档 commit 时代理封了 github.com

收尾提交 `99e2bcf`（README + memory）push 时开始报 `CONNECT tunnel failed, response 502`：
沙箱代理只放行 `api.github.com`，掐掉 `github.com`（**直连也超时**，沙箱没有直通出口）。
发布本身不受影响（CI 早已跑完），卡住的只是这一个文档 commit。

绕法：**GitHub Git Data API** 把本地 commit 原样搬上去 —— 上传变动文件的 blob → 自底向上重建
受影响的目录树（`.workbuddy/memory` → `.workbuddy` → 根，只有变动文件的祖先目录会变）→
用同一个 tree/parent/身份建 commit → `PATCH /git/refs/heads/main`。三个坑：

1. **只传 blob 会 422 `Tree SHA does not exist`** —— tree 对象本身也必须先建。
2. ⚠️ **`git ls-tree <commit> <dir>/` 的条目名是全路径**（`.workbuddy/memory/x.md`），
   拼 child 会变成 `.workbuddy/.workbuddy/memory` ⇒ 递归落空 ⇒ 父树沿用没上传的子 tree ⇒ 422。
   要用对象语法 `git ls-tree <commit>:<dir>`（条目名才是相对名）。
3. **GitHub 把时间戳规范化成 UTC**（本地 `+0800` → 远端 `Z`）⇒ 远端 commit SHA 与本地不同
   （内容相同、tree 相同），试过补 message 末尾换行也不命中。网络恢复后 fetch + reset 对齐。

远端 `8bd1142`；本地已 `reset --hard origin/main` 对齐（先验证两边 tree 都是 `9582b4fa…` 才 reset）。
约 10 分钟后 `github.com` 自愈（fetch 成功）。

这条工作流已固化成 skill **`github-api-push-fallback`**（含 `scripts/api-push.py`，支持 `--dry-run`；
已用一个游离 commit 实测：blob 校验 + 三层 tree 重建全过、ref 未动）。用户级记忆与
`tauri-gh-release-verify` 的环境坑一节都加了指引。

## 下午（14:1x）：探索「悬浮窗压住任务栏」的更好方案（事件驱动替代 500ms 轮询）

用户：「现在悬浮窗拖到任务栏上，置顶逻辑类似定时器唤醒置顶，探索更好的方案」。
先做了 5 轮真机探测（**全程用自建 topmost 测试窗口，没碰用户正在跑的实例**），
脚本 `.workbuddy/tmp/probe-topmost-events{,2,3,4,5}.py`。

### 推翻了旧笔记的一句结论
旧笔记写「任务栏被提到最前**不会给应用发任何事件**」。那只对**窗口消息/Focus 事件**成立 ——
**WinEvent 层面是有事件的**：任务栏提升 = 一次 z 序重排 ⇒ **桌面窗口（类 `#32769`）收到
`EVENT_OBJECT_REORDER`**。实测 3/3、再 5/5 次全部收到，延迟**同刻**（消息投递毫秒级；
记录点比事件还晚 41~44ms）。钩子可装在**没有窗口的后台线程**上（5/5 收到）。

### 实测数据（决定方案的关键）
| 观测 | 结果 |
|---|---|
| 空闲 3s | 桌面 reorder **0** 条（有交互时约 2.8 条/s） |
| 我们的纠正动作自身 | 产生 **4** 条桌面 reorder ⇒ 必须节流 + 靠「检查当前状态」收敛 |
| `EVENT_SYSTEM_FOREGROUND` | 任务栏提升时**不发**（只有 Win 键路径发）⇒ 不能当触发源 |
| 真实鼠标点任务栏**空白处** | 发 2 条 reorder 但**任务栏并没有提升**（被压=False）⇒ 空白点击不构成遮挡 |

### 已否决的方案（都有实测依据）
- **owner = 任务栏句柄**（想让 owned window 恒在 owner 之上）：**严格对照实验否决** ——
  无 owner 能压住 ✓ / 设 owner 后照样能压住 ✓ / 拆掉又能压住 ✓。
  ⚠️ 第一次跑得出「owner 生效」是**假绿**：当时**没先验证 shove 本身有效**，正是老笔记里
  「shove 成功率约一半、必须重试到成功」那个坑。
- uiAccess / 更高 window band：要签名 + 装 Program Files，本项目装 `%LOCALAPPDATA%`，用不了。
- AppBar：解决的是「预留屏幕空间」，不是 z 序竞争，还会挤开别的窗口。
- `WH_MOUSE_LL` 全局鼠标钩子：触摸/键盘路径漏、拖慢全局鼠标、回调超时会被静默卸载。

### 推荐方案（用户已拍板「按推荐方案重构」）
事件驱动替换轮询：`SetWinEventHook(EVENT_OBJECT_REORDER, …, WINEVENT_OUTOFCONTEXT)` + 后台线程
阻塞消息循环 → 回调里 `is_buried_by_taskbar()` → `raise()`；节流 100ms 防自重入；
把阻塞的 `GetMessage` 换成 `MsgWaitForMultipleObjects` 顺带做兜底检查（hook 失效还有救，
且不用第二个线程）。收益：纠正延迟 0.2~0.4s → 毫秒级；空闲不再周期性醒来。

## 下午（14:3x）：落地 —— 悬浮窗 z 序守护改成事件驱动

把 `lib.rs` 里的 `watch_mini_above_taskbar`（500ms 轮询）+ `mod taskbar` 拆成 `src-tauri/src/taskbar/`：
- `zorder.rs`：纯 Win32（`is_buried_by_taskbar` / `raise` / `is_visible`；类名匹配带单测，遍历上限 64 步防转死）。
- `guard.rs`：`SetWinEventHook(EVENT_OBJECT_REORDER, …, WINEVENT_OUTOFCONTEXT)` + 后台线程
  `MsgWaitForMultipleObjects(2000ms, QS_ALLINPUT)` 循环；**回调是空实现**（事件本身就会把循环唤醒，
  在回调里做重活会拖住消息派发）；每轮醒来按 可见 → 被压 → 100ms 节流 → `raise` 的次序处理。
- `mod.rs`：只暴露 `start()` / `set_mini_hwnd()`，非 Windows 留空实现。
- `create_mini` 里把 `hwnd` 登记进去 ⇒ 守护线程只碰 HWND + 纯 Win32，**不回主线程**（那会把延迟加回去）。

⚠️ `SetWinEventHook` 返回的是 `HWINEVENTHOOK`（不是 `Result`），判失败要用 `hook.0.is_null()`。

### 验收
- `cargo check --all-targets` ✓ 无警告；`cargo test --offline` **11/11**（新模块两条断言在 `taskbar::zorder::tests`）。
- 真机 `verify-mini-taskbar.py` **全绿**：纠正延迟 **1.0~1.9ms**（旧版 200~400ms），3 轮 referee 对照全成立。

### ⚠️ 验证脚本里两处必须保留（都是真踩到的）
1. **绝不能用 `taskkill /IM market-monitor.exe`** —— Windows 的 `/IM` **不区分大小写**，而用户安装版的 exe
   实测就叫 `market-monitor.exe`（`%LOCALAPPDATA%\MarketMonitor\market-monitor.exe`）⇒ 一条命令会把
   用户正在跑的实例一起杀掉。改成**只按 pid** 收尾，并且**按 pid 认领窗口**（别人的实例也有同名悬浮窗）。
2. **referee 对照**：脚本自建一个**无人守护**的 topmost 窗口，shove 之后它必然被压、且 300ms 后仍被压 ——
   用它证明「任务栏真的提到了最前」这件事发生了。没有这条，「悬浮窗没被压住」会被误读成「已纠正」= 假绿。
   referee 的基线同样要用「先降 NOTOPMOST 再升 TOPMOST」造（对已是 topmost 的窗口直接提可能 no-op）。
