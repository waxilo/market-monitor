## 桌面端（续）：遮罩卡住 + 任务栏遮挡

用户两条反馈：①「遮罩有时候鼠标不在上面也显示，像卡住」②「悬浮窗放在任务栏上，再点任务栏，悬浮窗会被覆盖」。

### 1. 遮罩改成显式状态（不再用 CSS `:hover`）
新增 `hooks/useOverlayReveal.ts`：`pointermove` 才能点亮；离开面板 / 窗口失焦 / 页面不可见 / 视口 resize / Tauri 的 `onMoved`·`onResized`·`onFocusChanged(false)` 一律熄灭；默认熄灭。`MiniApp` 给 `.mini` 加 `revealed` 类，theme.css 的 `.mini:hover .mini-overlay` → `.mini.revealed .mini-overlay`，行的 hover 底色同样收进 `.revealed`。
- 根因：`:hover` 只在浏览器真收到鼠标消息时更新，而这个窗口会自己移动（拖拽 / 按条数改高度时下边缘不动⇒上边缘在跑）和隐藏，鼠标位置在那之后离开窗口时 **Chromium 再也不发 `mouseleave`** ⇒ `:hover` 永久卡亮。
- 指针事件挂在**面板元素**上而不是 window：要的是「指针在面板上」，视口比面板大时两者结论不同。

### 2. 压住任务栏（`lib.rs` 的 `taskbar` 模块 + `watch_mini_above_taskbar`）
- `is_buried_by_taskbar(hwnd)`：沿 `GetWindow(GW_HWNDPREV)` 只遍历 topmost 组（碰到第一个非 topmost 就停，topmost 永远在非 topmost 之上），遇到 `Shell_TrayWnd`/`Shell_SecondaryTrayWnd` 即被压住。
- 500ms 心跳线程 + `run_on_main_thread`：**只在真被压住时**用 `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE|NOSIZE|NOACTIVATE)` 提回去；无条件重设会周期性压住开始菜单等其它 topmost 窗口。
- 为什么必须轮询：任务栏被点击/激活时被 shell 提到最前，**这件事不会给应用发任何事件**（用户点的是任务栏，连 `Focused(false)` 都收不到）。
- Cargo.toml 加 `[target.'cfg(windows)'.dependencies] windows = "0.62"`（与 tauri 同版本，复用 lock 里的 0.62.2，不新增下载）。

### 验收
- `npm run build` ✓、`cargo test` 8/8 ✓（新增两条任务栏类名断言）。
- `verify-desktop-ui.mjs` **21/21**（新增 4 条遮罩开关断言：默认不显示 / 指针离开熄灭 / 失焦熄灭 / 尺寸变了熄灭 / 还能再点亮）。
- 新写 `verify-mini-taskbar.py`（真机 z 序判定）**全过**：复现「任务栏压住悬浮窗」→ 心跳 0.2~0.4s 纠正；任务栏处于激活态时同样有效。

### 排查过程中的三个关键发现
1. **`set_always_on_top(true)` 重复调用无效**：tao 的 `set_window_flags` 有 flags 去重（`diff == empty` 直接 return），`ALWAYS_ON_TOP` 早置位 ⇒ 根本走不到 `SetWindowPos`，必须自己调 Win32。
2. **对已经是 topmost 的窗口直接提 `HWND_TOPMOST` 也可能是 no-op** ⇒ 复现脚本先降 NOTOPMOST 再升 TOPMOST 才稳（且成功率约一半，必须**重试到真的被压住**，否则「没被压住」会被算成「已纠正」= 假绿，我第一次跑就吃了这个）。
3. 用**类名伪装成任务栏**的假窗口（ctypes `RegisterClassExW` + `CreateWindowExW("Shell_TrayWnd")`）把「判定 + 纠正」从「真实任务栏能不能被越过」里分离出来，才确定链路本身正常 —— 打包的 python 没有 tkinter。

## 傍晚：发版模型改成「每端一个固定通道 Release」+ 发桌面端 0.1.2

用户要求：把 Releases 清空，只留「一个 app + 一个桌面端」两个；以后每次发新版**只换里面的产物、不新建 Release**。
旧状态是两套写法各堆一串 —— 桌面端每次 `gh release delete` + `create`（每次都产生新 Release），
Android 每版按 tag 建一个，**已经堆到 39 个**（0.2.0 … 0.9.26 + desktop-v0.1.0 + desktop-latest）。

### 一、固定通道怎么落
- 新增 `.github/scripts/publish-channel.sh`（两端共用）：**通道不存在才创建**，存在就先**清掉上一次的全部产物**再传新的。
  ⚠️ 必须清：产物名带版本号（`market-monitor_0.1.1_windows.exe` → 下一版名字就变了），
  `gh release upload --clobber` 只覆盖同名文件，不清就会新旧并存、用户可能下到过期包。
- Android：`release.yml` 发到固定 tag `android-latest`。**版本号改由产物名承载**（`market-monitor-<version>.apk`），
  因为通道 tag 恒定、不再带版本。App 侧 `VersionCompare.versionFromAssetName` 从文件名读
  （取第一个 `数字.数字[.数字]`；`arm64-v8a` 这类 ABI 名不含点，所以 ABI 后缀加在版本后面是安全的）。
  另加断言：tag 版本必须 == `build.gradle.kts` 的 `versionName`，不一致直接红。
- Android App：`GithubReleaseApi.latestRelease()` → `channelRelease()`，`/releases/latest` → `/releases/tags/android-latest`；
  `ReleaseInfo.version`（读 tag）→ `apkVersion()`（读产物名）。

## 插曲：推文档 commit 时代理封了 github.com

收尾提交 `99e2bcf`（README + memory）push 时开始报 `CONNECT tunnel failed, response 502`：
沙箱代理只放行 `api.github.com`，掐掉 `github.com`（**直连也超时**，沙箱没有直通出口）。
发布本身不受影响（CI 早已跑完），卡住的只是这一个文档 commit。

绕法：**GitHub Git Data API** 把本地 commit 原样搬上去 —— 上传变动文件的 blob → 自底向上重建
受影响的目录树（`.workbuddy/memory` → `.workbuddy` → 根，只有变动文件的祖先目录会变）→
用同一个 tree/parent/身份建 commit → `PATCH /git/refs/heads/main`。三个坑：

1. **只传 blob 会 422 `Tree SHA does not exist`** —— tree 对象本身也必须先建。
2. ⚠️ **`git ls-tree <commit> <dir>/` 的条目名是全路径**（`.workbuddy/memory/x.md`），
   拼 child 会变成 `.workbuddy/.workbuddy/memory` ⇒ 递归落空 ⇒ 父树沿用没上传的子 tree ⇒ 422。
   要用对象语法 `git ls-tree <commit>:<dir>`（条目名才是相对名）。
3. **GitHub 把时间戳规范化成 UTC**（本地 `+0800` → 远端 `Z`）⇒ 远端 commit SHA 与本地不同
   （内容相同、tree 相同），试过补 message 末尾换行也不命中。网络恢复后 fetch + reset 对齐。

远端 `8bd1142`；本地已 `reset --hard origin/main` 对齐（先验证两边 tree 都是 `9582b4fa…` 才 reset）。
约 10 分钟后 `github.com` 自愈（fetch 成功）。

这条工作流已固化成 skill **`github-api-push-fallback`**（含 `scripts/api-push.py`，支持 `--dry-run`；
已用一个游离 commit 实测：blob 校验 + 三层 tree 重建全过、ref 未动）。用户级记忆与
`tauri-gh-release-verify` 的环境坑一节都加了指引。

## 下午（14:1x）：探索「悬浮窗压住任务栏」的更好方案（事件驱动替代 500ms 轮询）

用户：「现在悬浮窗拖到任务栏上，置顶逻辑类似定时器唤醒置顶，探索更好的方案」。
先做了 5 轮真机探测（**全程用自建 topmost 测试窗口，没碰用户正在跑的实例**），
脚本 `.workbuddy/tmp/probe-topmost-events{,2,3,4,5}.py`。

### 推翻了旧笔记的一句结论
旧笔记写「任务栏被提到最前**不会给应用发任何事件**」。那只对**窗口消息/Focus 事件**成立 ——
**WinEvent 层面是有事件的**：任务栏提升 = 一次 z 序重排 ⇒ **桌面窗口（类 `#32769`）收到
`EVENT_OBJECT_REORDER`**。实测 3/3、再 5/5 次全部收到，延迟**同刻**（消息投递毫秒级；
记录点比事件还晚 41~44ms）。钩子可装在**没有窗口的后台线程**上（5/5 收到）。

### 实测数据（决定方案的关键）
| 观测 | 结果 |
|---|---|
| 空闲 3s | 桌面 reorder **0** 条（有交互时约 2.8 条/s） |
| 我们的纠正动作自身 | 产生 **4** 条桌面 reorder ⇒ 必须节流 + 靠「检查当前状态」收敛 |
| `EVENT_SYSTEM_FOREGROUND` | 任务栏提升时**不发**（只有 Win 键路径发）⇒ 不能当触发源 |
| 真实鼠标点任务栏**空白处** | 发 2 条 reorder 但**任务栏并没有提升**（被压=False）⇒ 空白点击不构成遮挡 |

### 已否决的方案（都有实测依据）
- **owner = 任务栏句柄**（想让 owned window 恒在 owner 之上）：**严格对照实验否决** ——
  无 owner 能压住 ✓ / 设 owner 后照样能压住 ✓ / 拆掉又能压住 ✓。
  ⚠️ 第一次跑得出「owner 生效」是**假绿**：当时**没先验证 shove 本身有效**，正是老笔记里
  「shove 成功率约一半、必须重试到成功」那个坑。
- uiAccess / 更高 window band：要签名 + 装 Program Files，本项目装 `%LOCALAPPDATA%`，用不了。
- AppBar：解决的是「预留屏幕空间」，不是 z 序竞争，还会挤开别的窗口。
- `WH_MOUSE_LL` 全局鼠标钩子：触摸/键盘路径漏、拖慢全局鼠标、回调超时会被静默卸载。

### 推荐方案（用户已拍板「按推荐方案重构」）
事件驱动替换轮询：`SetWinEventHook(EVENT_OBJECT_REORDER, …, WINEVENT_OUTOFCONTEXT)` + 后台线程
阻塞消息循环 → 回调里 `is_buried_by_taskbar()` → `raise()`；节流 100ms 防自重入；
把阻塞的 `GetMessage` 换成 `MsgWaitForMultipleObjects` 顺带做兜底检查（hook 失效还有救，
且不用第二个线程）。收益：纠正延迟 0.2~0.4s → 毫秒级；空闲不再周期性醒来。

**而 `cargo build` 退出码 0、应用照常构建运行** —— 这个不对称是关键线索。

### 证据链（每条都是实测）
1. **不是并发**：dev 会话空闲时重跑 `cargo check`，依旧 ICE。
2. **不是 `build.rs` 那行**：`CARGO_INCREMENTAL=0 cargo check` → **exit 0 / 13.92s**。
   ⇒ 问题**只在增量编译这条路径**上。
3. **写增量缓存失败只是 warning** ⇒ build 照过（退化成非增量），但 rustc 之后仍按增量流程读回并编码 rmeta → 读到不一致状态 → ICE。
   `cargo build --lib` 自己把机理打了出来：
   `error copying object file ...\deps\rmetaXXXX\full.rmeta to incremental directory as ...\s-xxx-working\metadata.rmeta: 拒绝访问 (os error 5)`
4. **`s-xxx-working` 残留 = 最好的自证**：正常流程是「先把上一版拷进 `-working`，编完改名并删旧版」，
   看到 `-working` + `.lock` 残留就说明上一次运行时被中断/失败，这个 session dir 已脏。
5. **权限没问题，是句柄**（这条推论省了大量时间）：`shutil.rmtree` 掉 session dir 里的子目录**成功** ——
   删目录需要 DELETE 权限，所以权限够 ⇒ 唯一解释是**目录内有打开的文件句柄**。
   佐证：26 个 session dir **全部**改名失败（09-28 到刚刚写的都一样），而我**新建的空目录**改名正常。
6. **找不到具体持有者，且不该再找**：Restart Manager 返回 `RmGetList 0x00000005`（拒绝访问）
   ⇒ 答案集里有**受保护进程**（`SearchIndexer.exe` 在场且命令行读不到）。枚举全系统句柄被**沙箱直接 SIGTERM**（敏感操作，合理）。
7. **本机有宿主注入的删除拦截层**：`shutil.rmtree(incremental)` 处理 3210 个 / 3155 MB 文件，
   只在最后顶层报 1 个错，**而文件一个都没少**；stderr 是
   `[safe-delete][SAFE_DELETE_FAIL_CLOSED] {"reason":"trash-failed", ... "Some operations were aborted"}`。
   它把删除**改道回收站**，改道失败后**仍向调用方报告成功** ⇒ **删除类工具的输出不能当事实，必须回读校验**。
   而在同一台机器上 rustc 报的 `os error 5`，很可能就是同一层拦截（子进程会继承）。
   ⇒ 结论应写成「有 X 层在拦」，而不是「磁盘/权限坏了」。

### 决定：**不为它改仓库配置**
`[profile.dev] incremental = false` 能绕过去，但那是**永久拖慢用户日常构建**去绕过一个**可能只存在于我的工具沙箱**里的问题
—— 正是用户明确反对的缝补。正确做法：把证据交给用户，让他在**自己的终端**跑一次 `cargo check` 验证是否复现，再决定。
本轮需求不受影响（`npm run build` ✓、`cargo build` ✓、dev 会话 ✓）。
`target/debug/incremental` 已确认**未被损坏**（删除尝试是假成功，3210 个文件原样还在）。

### 顺带查清的两件事
- **那个 `cargo run`（tauri dev）是用户的 dev 会话，一条都不能动**：
  `node tauri.js dev`(41140) → `cargo run`(54276→39772) → **`target\debug\market-monitor.exe`(pid 34216)** + 挂在它下面的 WebView2。
  `tauri dev` 会 watch `src-tauri` ⇒ 我改 `build.rs` 触发了它**自动重启**（16:44:34 cargo run / 16:44:52 app），
  正好落在我那次重建上 ⇒ 用户窗口里跑的就是新 exe；前端走 vite dev server（HMR）。

### 三个值得记住的坑

1. **Kotlin 块注释支持嵌套** ⇒ 在 KDoc 里写 `` `.../market/*` `` 会把这个 `/*` 当嵌套注释起点，
   整块注释永远闭合不上，报 `Unclosed comment` 且**行号指向文件末尾**（极难联想）。文案里别出现 `/*`。
2. **HTX 的 `from`/`to` 完全无效**（`start`/`end` 也不行）：用一个明显过期的窗口请求，回来的仍是当下最新 N 根。
   所以 `klines` 不传时间窗，并给方言接口加了 `supportsTimeWindow`；否则 `olderKlines` 的
   `hasMore = raw.size >= rawLimit` 会恒真 ⇒ 用户拖到最左**无限重复请求**同一批数据。
3. **两家「不支持」的形态不同，得分别兜**：HTX 是 `HTTP 200 + status:"error"`（业务码不在 HTTP 状态里，要抛）；
   Bitunix 是 `code:0 + data:[]`（不报错也不回落 ⇒ **没抛异常 ≠ 周期被支持**，靠白名单挡）。

## 本轮踩到的四个坑（都不是产品缺陷，但都会把结论带偏）
1. **`:app:compileDebugKotlin` 报「删不掉 `app/build/tmp/kotlin-classes\debug\com`」时，先想 IDEA**。
   文档（`basedata/2026-09-29_…候选.md` 第六节的 ⚠️）已定过性：**用户开着的 IDEA 占着这个目录**，
   `./gradlew --stop` 只停 Gradle daemon、停不掉 IDEA（也**不要去杀 java 进程** —— IDEA 与它的
   `RemoteMavenServer` 在同一个 `jps` 列表里）。本次新验证的处置同样有效且更省事：
   **把旧目录 `os.rename` 走**（`kotlin-classes` / `build/kotlin` / `kspCaches` 三个一起，
   改完回读确认），Gradle 就会在**新路径**上重建，IDEA 抓的是旧路径 ⇒ 一步通。
   文档里那套 `-I init-builddir.gradle --project-cache-dir` 是把 `buildDir` 整体挪走，等价且更彻底。
   附带两条噪声**别当成第二个 bug**：并发跑两个 Gradle 会互相抢同一批目录（本次确实有三个残留任务在跑）；
   `./gradlew --stop` 会把正在跑的那个也停掉，它的失败文案是
   `Gradle build daemon has been stopped: stop command received`。**同一项目一次只跑一个 Gradle。**
2. **开着的构建缓存会伪装成编译失败**：`Failed to store cache entry … Could not get file mode for X.class`。
   `--no-build-cache` 一跑就能区分「缓存写盘失败」与「真的编不过」。
3. ⚠️ **同一路径的两次读取给出了不同内容**，本次两例：`FuturesDialects.kt` 的 KDoc 先读到
   `linear-swap-ex/market/*`（会触发 Kotlin 嵌套注释的旧写法）、后读到已改成中文文案的版本；
   测试文件先读到第 547 行是 `allTickers`、后读到 `exchangeInfo` —— 后者恰好**少了那 4 行断言**，
   与「文件在此期间被改动」完全吻合（用户开着 IDEA，很可能就是他自己顺手修的）。
   ⇒ 教训不是「哪个工具坏了」，而是：**要判定「文件里到底有什么」就回读原文（python / grep）**，
   **要判定「编译过不过」只看编译器输出** —— 别拿某一次读取的渲染去"修"一个可能已经不存在的 bug
   （本次差点白改一轮；也说明这个仓库的改动可能**并发来自 IDEA 侧**，动手前先回读一次更保险）。
4. Kotlin 块注释**可嵌套**的坑（KDoc 里写 `/market/*` ⇒ 整块注释闭合不上，报 `Unclosed comment`
   且行号指向文件末尾）已写进 `android/basedata/2026-09-29_行情来源独立性与可接入候选.md` 第六节。

### 本轮踩到：远端 main 有个「内容相同、SHA 不同」的提交
`git push origin main` 被拒（`! [rejected] main -> main (fetch first)`）。**不是别人推了东西**，而是上次发
0.1.5 时 `git push` 不通、走了 **Git Data API 重建**（时间戳被规范成 UTC）⇒ 远端 `ff4a0dd` 与本地 `8f69de2`
是**同一个提交的两种 SHA**。判定与处置（这次实测很干净）：
1. 先证等价：`git rev-parse A^{tree} B^{tree}` 两者相等 + `git diff --stat A B` 为空 ⇒ 内容确实一致
   （本次都是 `665ae30…`）；
2. 再换基：`git rebase --onto origin/main 8f69de2`，把本地新提交重放到 `ff4a0dd` 上；
3. 重推即成功（`ff4a0dd..8e65cb2`）。
⚠️ 副作用：本地 `desktop-v0.1.5` tag 指向游离的 `8f69de2`，而远端同名 tag 指向 `ff4a0dd`。
推 tag 时**只写要发的那几个名字**，别用 `--tags`（会拿同名旧 SHA 去撞远端）。





## 桌面端：两点画直线（趋势线）

需求一句话：「market-monitor 桌面端支持两点画直线」。两个设计点问过用户：① 形态选**贯穿全图的直线**
（不是 A-B 线段）② 编辑方式选**线身平移 + 端点改角度**（右键删、锁住全停）。

### 落地
- 新增 `desktop/src/lib/trendLines.ts`（零依赖纯函数）+ `chartMath.ts` 加 `timeIndexOf`/`timeAtIndex`
  （严格互逆的时间锚点换算）；`hooks/usePriceLines.ts` 扩成 `hooks/useDrawings.ts`（两种线 + 一把锁）。
- 交互：指标条末尾新增「直线」chip 进画线模式 —— 图上**点两下**或**按住拖**都成线；Esc / 右键退出；
  未锁时抓取优先序 把手(6px) → 直线线身(4px) → 水平线；锁住后画线、拖拽、右键一概不生效（清空也不给）。
- 锚点用**时间戳 + 价格**而不是蜡烛下标：序列是滚动 300 根窗口，下标会漂，时间戳不会。
- 绘制与命中判定共用同一个 `anchorPx`（这仓为「两处各写一份映射」吃过亏）。

### 验收（两个脚本都在 `.workbuddy/tmp/`，Node 直跑，不碰网络）
- `verify-trend-lines.mts`：**140 条纯函数**全过（坏存储值 / 增删 / 平移与绕端点转 / Liang–Barsky 裁剪含
  水平·垂直·陡线·擦角点·整线在外 / 命中容差边界 / 时间换算往返含缺口与单根 / 100 点单调性扫描）。
  ⚠️ 写测试时两次把「端点在外」当成「线不过矩形」—— **无限直线的语义下端点在外不等于线不在界内**，
  改成用真实不过矩形的两条线（y=x+200、y=-x+200）才立住。
- `verify-trend-lines-ui.mjs`：**68 条真实渲染**全过。自建静态服务器伺服 `desktop/dist` + 预注入 fetch 桩
  （Gate 现货三接口 + 确定性 300 根 K 线：增量轮询拿到的末根与 300 根系列逐字段相同 ⇒ 两个快照之间画面不自变）。
  像素判据：线色像素数、列增量、**左右边缘条带都有差异**（这条专门钉「贯穿全图」——A-B 线段在两端条带里是空的）、
  拖线身的像素位移 == 拖拽距离、拖端点后线仍穿过另一端、刷新后锚点逐字节相同、平移/缩放后锚点不变。
- 脚本里两个坑：① 页面内的 `__rowsAt` 一开始把 `.data` 取了两遍（`base.data.data`）② 阶段 1 的守卫测试
  顺序写反了（先点主图会产生待定、再点主图就成线）—— 都是**测试自己的错**，改测试而不是改产品。
